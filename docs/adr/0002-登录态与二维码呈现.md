# 0002. 登录态与二维码呈现

- 状态：已采纳（协议细节见 [iLink：登录与绑定](../protocol/ilink-登录与绑定.md)）
- 日期：2026-11-07

## 背景

iLink 的接入凭据由扫码换取：`get_bot_qrcode` 返回二维码标识与待编码文本，轮询 `get_qrcode_status` 直到 `confirmed`，拿到 `bot_token`、账号 id 与运行域名。状态名、TTL、域名规则都是外部事实，见 [iLink：登录与绑定](../protocol/ilink-登录与绑定.md)。

要定的两件事：

1. **登录态存哪里、存什么。** 桥重启后要能接着收消息，不能每次启动都扫码；但 token 属于凭据，红线是不能进日志、不进面板快照、不随包发布。
2. **二维码怎么给主人看。** 面板是 Web，插件零运行时依赖（ADR-0001），没有二维码渲染库；`qrcode_img_content` 是**待编码的文本**而不是图片。

## 决策

- **登录态落本机状态文件** `$DSH_HOME/dsh-im-wechat/login.json`（`DSH_HOME` 缺省 `~/.dsh`）。目录 `0700`、文件 `0600`，写入走「临时文件 + rename」原子替换。文件内容只有：`botToken`、`account`（`ilink_bot_id`）、`userId`、`baseUrl`、`loggedInAt`、`version`。
- **登录态只经 `LoginStateStore` 读写**，`describe()` 一类对外快照只回「已登录 / 账号尾号 / 登录时间」，永不回 token。日志里 token、`ilink_bot_id` 一律脱敏成布尔或尾号。
- **登录由 host 半驱动**：面板调 `login.start` 起一次会话，host 自己长轮询状态机并在成功后落盘；面板只轮询 `login.status` 读内存快照。这样面板切走、刷新都不会中断扫码，也不会出现「两个标签页各轮询一份」。
- **二维码呈现**：面板里以 QR 图片呈现，编码器自写（`src/shared/qr.ts`，零依赖）；同时**始终显示 `qrcode_img_content` 原文链接与复制按钮**作为兜底——官方实现本身就提示「二维码无法使用时可以访问该链接」，链接是协议的既定用法而不是降级 hack。
- **状态机按官方行为对齐**：二维码 TTL、过期刷新次数、PIN、扫码后重定向、已绑定，逐条对照协议文档实现，不自己发明边界。
- `baseUrl` 以 `confirmed` 返回的 `baseurl` 为准并落盘（未返回时退回 `https://ilinkai.weixin.qq.com`）；扫码期间的重定向只影响本次登录轮询，不乱改已保存的运行域名。

## 后果

- 凭据只在一处、权限收紧，面板与日志都拿不到 token；代价是主人换机器要重新扫码。
- 登录流程可以在没有面板时自测：host 的登录控制器不依赖面板，开发脚本直接驱动它即可。
- 自写编码器意味着多一份要维护的算法代码；用公开实现（仅测试期作 oracle，不进产物）生成的矩阵做逐元素比对，保证不是「看起来像二维码」。
- `qrcode_img_content` 是链接这一点被写进面板：任何渲染失败都不影响登录，主人还有可点的链接。
