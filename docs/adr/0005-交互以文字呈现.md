# 0005. 交互以文字呈现，不声明交互卡能力

- 状态：已采纳
- 日期：2026-11-07

## 背景

`my-superagent/v1` 的 `Delivery.interaction` 是结构化的问题与选项（和 DSH 的 `ask_user_question` 同构），桥可以声明 `capabilities.interaction` 表示自己有卡片能力，此时核心会走 `BridgeHandle.answer()` 收作答。

微信这条渠道没有交互卡：iLink 只能发消息条目，发出去的消息不能改，也没有可点的按钮。另一方面，核心把 `interaction` 原样放进 `Delivery`，**并不会**替桥把题目写进正文——`interactionMarkdown` 在核心侧目前没有调用方。所以「桥不处理 `interaction` 会怎样」的答案是：主人收到一条只有结论、没有选项的消息，无从作答。

核心对文字作答的匹配规则是确定的（`answerFromText`）：单题回序号、选项文字或多选逗号分隔；多题按「；」「。」或换行分段，段数对上就一段一题；计划审阅认「批准 / 1 / approve」与「继续规划」。

## 决策

- **不声明 `interaction`**：桥上不带 `capabilities.interaction`，核心因此不会走 `answer()` 路径，也不会尝试改卡。`BridgeCapabilities.interaction` 省略即可，声明成全 `false` 只是把「没有」写成六个字段。
- **把交互写进正文**（`src/host/superagent/render.ts` 的 `renderInteraction`）：单题列选项并提示「回复序号选择（多选用逗号分隔），或直接回复文字作答」；多题按题目顺序编号并提示分行作答；计划审阅单独给「回复批准执行 / 回复其他文字作为修改意见」。
- 提示语与核心的解析规则**逐条对齐**，不发明新格式：任何一边改规则都要同步改另一边，否则主人按提示作答会被当成普通消息。
- 交互的答案由核心从普通消息里匹配，桥不保存任何「等待作答」的状态，也就不存在重启后卡片失效的问题。

## 后果

- 主人在微信里看到的是可读的编号列表，回复文字即可，行为与 Web 端一致。
- 没有卡片，就没有「作答后更新卡片」的能力，`updateAfterAnswer` 之类的字段也就无需定义。
- 呈现层多了一段与核心解析规则耦合的逻辑；这层耦合由单测（`test/unit/render.test.ts`）钉住格式，改格式时会被迫写测试。
- 将来微信若支持可点消息，接缝是：声明 `interaction`、实现 `answer()`、把 `renderInteraction` 换成卡片，其余协议层不动。
