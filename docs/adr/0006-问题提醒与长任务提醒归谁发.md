# 0006. 问题提醒与长任务提醒归谁发

- 状态：已采纳
- 日期：2026-11-08

## 背景

桥接上核心之后，「有事找主人」有两条路径：

- **核心负责**：`dsh-my-superagent` 把提问与提醒做成 `Delivery`，桥只负责呈现（ADR-0005）；
- **插件自己负责**：DSH 宿主本身有 `user-questions/request`（waterfall，监听器直接返回答案）与 `session/event`（回合开始/结束、助手消息），插件可以自己发提醒、自己收答案。

两条路都做就会**重复打扰**：主人收到两遍同一条问题。如流桥的解法是「接入核心后自有关闭」，它的面板上写着「已接入我的超级助理，提醒与通知改由核心负责，此处暂停」。

同时，主人要求能不能**不接入核心**：只当微信通知与作答通道用。这时没有任何人发提醒，插件必须自己顶上。

## 决策

- 面板上加 **「接入我的超级助理」开关**，默认接入（保持现有行为），可关闭。
- **互斥分工**：接入核心时插件不注册桥？——不，反过来：接入时注册桥、**自有关闭**；关闭时不注册桥、**自有功能接管**。判据只有一处：

  ```
  ownFeatures = 启用 && 未接入核心 && 已登录 && 未停机
  ```

- **问题提醒（文本）**：监听 `user-questions/request`，注册在链首（`prepend`）——Web 端的转发监听器在 Host 启动时就注册了，排在它后面永远轮不到。
  - 只对**根会话**提醒（`agent.session.header.origin !== 'subagent'`），子代理的提问不打扰主人；
  - 与 Web **竞答**：先把 `request.signal` 换成「原信号 ∪ 本地信号」，微信先答就 abort 本地这一份，Web 的投递随之作废；
  - 主人在微信里回的那句话按与核心一致的规则匹配（序号 / 选项文字 / 多选逗号 / 多题分段 / 计划审阅的批准词），匹配不上就交回普通消息路径；
  - 发不出提醒（没登录、没令牌）就**不接管**，原样交给 Web。
- **长任务提醒（文本）**：监听 `session/event`，跟踪根会话的 `turn/start` → `assistant/message` → `turn/end`；**超过阈值（默认 30 分钟）**的回合结束时发一条「标题 + 耗时 + 目标 + 结果 + 结论」。回合里主人插过话（`user/message` 且来源是用户/作答）就不发——那说明不是无人值守。
- 两者都用**文本**：桥没有交互卡（ADR-0005），问题提醒直接把题目与选项写成文字，主人回一句话即可。
- 提醒内容**不含**会话 id；标题取不到时用「未命名会话」，绝不把 id 兜底给主人。

## 后果

- 主人在接入核心时只收到核心的提醒，不接入时收到插件的提醒，任何时刻都只有一份。
- 插件的提醒链路与核心解耦：核心不可用、不需要、没装，通知与作答照常。
- 两道提醒共用一套文字渲染（`shared/question-text.ts`）与一套作答匹配（`host/answer-text.ts`），格式不会一会儿一个样。
- 竞答意味着「谁先答用谁」：微信答了就作废 Web 那份投递，不需要主人再去 Web 点一次。
- 长任务阈值默认 **30 分钟**，可配：profile 的 `longTaskThresholdMinutes` 给静态默认，面板上的「提醒阈值」落在 `config.json` 并优先于它（范围 1–1440 分钟）；改完立即生效，不用重连微信。
