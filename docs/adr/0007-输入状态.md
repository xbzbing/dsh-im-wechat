# 0007. 输入状态（正在输入）

- 状态：已采纳（字段与真机结论见 [iLink：消息与媒体](../protocol/ilink-消息与媒体.md)）
- 日期：2026-11-08

## 背景

主人在微信里发出一条消息后，到核心的第一条交付送达之间，微信那头毫无反馈——大模型可能在思考、排队、跑工具，主人分不清「正在处理」还是「没发出去」。iLink 有对应的主动接口（取 ticket → 发状态 → 保活/取消），本项目此前只收发消息，不用它。

这带来一个选择：输入状态该挂在哪两个时刻。官方实现挂在「整个回合」；本插件只有桥的回调，能观测到的是「核心受理」与「交付进入投递」。版本、ticket 缓存、失败退避这些细节都是协议事实，见 [iLink：消息与媒体](../protocol/ilink-消息与媒体.md)。

## 决策

- **时机（近似官方的「回合开始 → 回合结束」）**：
  - 核心**受理**入站消息（`receive` 返回 `accepted`）→ 发 `status=1`；
  - 桥**第一次尝试把交付发给该收件人**（`deliver` 进入）→ 发 `status=2`——交付一出现，模型的产出就到微信了，输入状态失去意义（流式进度首段到达同理）；
  - **10 分钟兜底超时**：核心一直没有交付（崩溃、消息被路由走），输入状态不能永远挂着；
  - 停轮询、登出、停用、切出核心接入 → 取消全部输入状态。
- **只有接入核心时才发**：单独安装模式没有大模型在思考，发了就是误导；也因此不进 `ownFeatures` 判据（它不是「提醒主人」，是协议层状态）。
- **纯尽力而为**：取 ticket、发状态的任何失败只记日志，绝不影响收发主链路；`typing_ticket` 取不到就安静地不显示。陌生人触发不了——只有核心受理（即核心认定是主人）才开始。
- **逃生门**：静态配置 `typingIndicator`（profile patch）默认开，真机行为不符预期时可关；面板不加开关，契约版本不动。
- 实现拆在 `host/typing.ts`（状态机与 ticket 缓存）+ `ilink/api.ts` 的 `sendTyping`，桥只加一个 `onDelivered` 回调。

## 后果

- 主人发完消息立刻能看到反馈，长思考不再像「石沉大海」；首段交付一到就消失，不会盖住内容。
- 多出的协议请求有上界：每人一次 `getconfig`（24 小时缓存）+ 思考期间每 5 秒一条 `sendtyping` + 一条取消，全部失败无用户可见影响。
- 时机是**近似**：受理即开、首投即关，与官方「整个回合」不完全一致——中途核心发了别的交付（提醒、摘要）会提前关掉输入状态，属可接受的误差。
- 2026-11-08 微信 Mac + iOS 实测两端都显示「对方正在输入」；同时发现取消后客户端仍会展示约 10 秒，因此「回复已到、输入中还在几秒」是客户端的展示时长，不是取消丢失，不要当 bug 修。要彻底去掉只能关掉 `typingIndicator`。
