# 0008. 微信原生 Markdown 与出站文本过滤

- 状态：已采纳（同日修订：初版「手机端按纯文本渲染」的结论被实测推翻；渲染能力见 [微信-客户端渲染](../protocol/微信-客户端渲染.md)）
- 日期：2026-11-08

## 背景

微信机器人发出去的文本会被客户端按 Markdown 渲染。最初只用「换行 / 空行 / 列表」做对照，得出「PC 端渲染、手机端纯文本」的结论，于是把列表符号从 `• ` 改成 `- `，行内 Markdown 继续拍平。随后用完整 Markdown 对照消息复测，结论是**两端都能渲染**，差别只剩软换行。渲染对照表与官方过滤规则见 [微信-客户端渲染](../protocol/微信-客户端渲染.md)。

也就是说：桥的问题不是「客户端看不懂 Markdown」，而是少数构造客户端渲染不了，留着只会把原始标记露给主人。

## 决策

1. **不再拍平 Markdown**：`title` / `body` 原样透传，交给客户端渲染表格、加粗、代码块、标题、链接、引用。
2. 新增 `toWeChatMarkdown`（`src/host/superagent/render.ts`），顺序是关键：
   1) 围栏代码块与行内代码摘成占位符；
   2) `***…***` / `___…___`（粗斜体）先处理，再处理 `**…**` / `__…__` 加粗，都占位；
   3) 图片整段丢弃；`#####`/`######` 去井号留文字；`~~…~~` 去波浪线留文字；
   4) `*…*` / `_…_` 斜体：内容含中文就去标记，否则占位保留；
   5) 还原占位符，清行尾空白，连续空行收敛成一条。
3. 与官方实现的唯一差异：官方是流式过滤器，遇到任何 `~` 都吞掉（`~/x` 变成 `/x`）；我们发的是整条消息，只剥成对的 `~~…~~`，单独的波浪线原样保留。
4. 列表符号不再改写，`- ` / `1. ` 原样透传；之前 `• ` 的改写规则删除。
5. **软换行不做补救**：单个 `\n` 在 PC 折叠、手机保留，是两端渲染器差异；正文里的分行交给 Markdown 语义（空行、列表、表格）表达，不再靠插空行伪造换行。
6. **组装时按用途决定发不发标题**：交付带 `inReplyTo`（回应主人刚发的那条消息）时**只发正文**——一问一答的正文自己就说明是什么，顶上多一行「回复」只是噪音，核心的标题约定也是「回复不带标题」；但正文为空时仍发标题，宁可多一行，也不能发出一条空消息。主动推送（长任务提醒、提问提醒、失败提醒、摘要）没有 `inReplyTo`，照旧带标题。

## 后果

- 表格、代码块、加粗、标题层级在微信里恢复可读，长回答不再退化成一大段纯文字。
- 图片、`#####/######`、删除线、中文斜体被降级：客户端本来不渲染这些，留着只会把原始标记露给主人。
- 超长交付仍按换行切分（默认 1800 字符/条），可能把表格或代码块切成两条；需要时再改成按块切分。
- 一问一答在微信里变成「问一条、答一条」；如果哪天核心想用标题传达回复里的额外信息（例如「这一轮被拦下」），那种交付必须不带 `inReplyTo` 才看得见——这类结局目前本来就走主动推送。
- 同一条消息的段内软换行在两端表现不同，块级结构（标题、列表、表格、代码）两端一致；真机验收时一起看。
