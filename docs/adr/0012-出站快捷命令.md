# 0012. 出站入口：`/wechat` 命令与 `dsh-wechat-send` 命令行

- 状态：已采纳
- 日期：2026-11-09

## 背景

主人经常在**普通 Web 会话**里说「把这几张图通过微信发给我」。这条路原本不通：核心只在超级助理的任务交付流程里经桥发图（ADR-0010），普通会话没有交付对象；模型只能自己去读插件源码，再拼一段脚本 import 内部模块（`LoginStateStore`、`ContextTokenStore`、`createApi`、`uploadImage`、`sendImage`）才能发出去。

那次实测：为发 4 张头像，模型读了约 20 个源文件才拼出可用脚本。成本高，而且脚本是临时写的——协议细节一改（例如 `image_item` 的 `encrypt_type` 与顶层 `aeskey`）就悄悄漂移，脚本仍然「能跑」，发出去的却是灰块。

三条候选路子的取舍：

- **注册宿主工具**（`ctx.tools.register`）：`ToolDefinition` 要经 `@deepseek-ai/dsh-tools` 的 `defineTool` 做参数 schema 转换与校验；引宿主包违反本仓库「不 import 宿主包」的约定，也过不了 `verify-package.mjs` 的依赖检查。手写 `ToolDefinition` 等于赌未公开契约。**否决。**
- **斜杠命令**（`ctx.commands.register`）：`dsh-commands` 的契约是「human-command registry」，handler 的语义是 *execute without sending the command to the model*，派发入口 `ctx.commands.execute(...)` 只由 UI 适配器调用；模型侧没有对应工具，**模型调不到**。它解决「主人自己发」，不解决「模型发」。**采纳，作为人用入口。**
- **插件包自带命令**（`package.json#bin`）：复用 `src/host/ilink/*`，模型一次 bash 就能发。**采纳，作为模型/脚本入口。**

## 决策

- **两个入口、一份实现**：斜杠命令 `/wechat`（人用，可带输入框附件）与可执行命令 `dsh-wechat-send`（模型/脚本用，子命令 `status` / `text` / `image`）都只做「解析参数 → 读登录态与 `context_token` → 调 `src/host/ilink/*`」；参数解析与发送端口在 `src/host/cli.ts`，命令侧在 `src/host/command.ts` 复用同一套。
- 命令注册走 `injectOptional(ctx, 'commands', ...)`：缺该服务的组合（headless 之类）插件照常加载，只是没有这条命令。
- 命令声明 `input.attachments`，输入框拖进来的图片经宿主 `attachments.readImage` 读字节后发送；没有该服务时明确报错，不假装成功。
- **收件人恒为扫码登录的主人**（`login.json` 的 `userId`），不提供 `--to`。与桥一致：不新增「给第三方发言」的能力，命令只解决「主人给自己发」。
- **图片先发、正文后发**，与桥的顺序一致（文字里常写「图见上」）。
- 发图前按文件头校验类型（png/jpeg/webp/gif）、单张 ≤ 10 MiB、单次 ≤ 10 张：识别不了的直接拒，不发出去再排查。
- 缺 `context_token` 时给出可操作提示（先在微信里给机器人发一条消息）并非 0 退出，而不是静默失败——协议层会静默丢弃。

## 代价与取舍

- 两个入口的可见性不同：命令只出现在输入框，模型看不到；CLI 只在 shell 里，面板上看不到。要「模型主动发」只能用 CLI，要「主人顺手发」用命令。
- profile 的 `node_modules/.bin` 不在 `PATH` 上，所以要么软链到 `~/.local/bin`，要么用绝对路径调用。
- CLI 是独立进程，与宿主内运行期**只共享状态文件、只读不写**（登录态与 token），不会互相干扰；代价是它不感知运行期是否已被停用或 token 已暂停，判断只能靠服务端返回。
- `context_token` 过期后命令仍然发不出去：这是 iLink 协议的窗口限制，不是命令缺陷，提示里说清楚。
- 命令不参与核心的重试与回执，失败就是失败，由调用方决定是否重跑。
