# 0013. 声明 context_token 的推送窗口

- 状态：已采纳 · 窗口数值被 [ADR-0015](0015-推送窗口改为24小时.md) 修订（6 小时 → 24 小时）
- 日期：2026-11-09

## 背景

iLink 的主动推送必须回传主人最近一条消息带来的 `context_token`，它过期后 `sendmessage` 返回 `ret=-2`，桥把这次失败归类成 `window-closed`，核心把交付挂回 `pending` 等主人下次开口。

问题不在「发不出去」，在于**核心事先不知道发不出去**：桥在能力声明里只写了 `requiresPriorInbound: true`，没有 `windowMs`，核心只能看「有没有过入站」，于是窗口关了也照发——每分钟一次，永远失败，而且因为有别的桥可用时也不会换桥（核心只有「本地判定窗口已关」才跳过这座桥）。

另一头是可见性：这批卡住的交付在面板上只是「待发送」，回执里的原因要另开一条 RPC 才看得到。2026-11-09 从 11:26 到 21:00 积了 5 条，主人毫无察觉。

## 实测

有效期既没有文档，也不在 token 里。把落盘的 token 按 base64 解开（102 字节），第 24 字节起是一个 u32 秒级时间戳，等于入站消息的接收时刻；其余字段是随机与非时间数据，**没有任何过期或 TTL 字段**。所以只能从真实交付记录反推：

| 观察 | 值 | 结论 |
| --- | --- | --- |
| 最后一次成功发送 - 之前的最后一条主人消息 | 218 分钟（3 小时 38 分） | 有效期 > 3h38m |
| 首次 `ret=-2` - 之前的最后一条主人消息 | 503 分钟（8 小时 23 分） | 有效期 ≤ 8h23m |

公开复刻的说法从「约 90 秒」到「几小时到 24 小时」都有，与本地记录不符的以本地记录为准：90 秒那种解释不了 3h38m 仍成功。

## 决策

- **能力里声明 `outbound.windowMs = 6 小时`**（`TOKEN_WINDOW_MS`），介于实测区间中点。声明后核心在窗口外直接跳过本桥：不发请求、不产生 `ret=-2` 回执、不吃重试次数，有第二座桥时把交付让给它。
- **窗口从「收到 token」起算**，与核心的 `now - lastInbound < windowMs` 判定一致（核心用主人最后一条消息的时间，桥用 token 落内存的时间，两者同源）。
- **被拒时记录 token 年龄**（`ContextTokenStore.age`，只在内存，落盘不带时间）。多攒几次 `window-closed` 的年龄就能把真实边界夹得更紧，届时改 `TOKEN_WINDOW_MS` 一个常量即可；从磁盘灌进来的 token 年龄未知，日志报「未知」而不是猜。
- **不提供配置项**：这个值是实测结论，不是使用偏好。真实边界变了应当改代码并留下记录，而不是让每个部署各填一个数字。

## 代价

- 6 小时是区间中点，不是实测值。若真实边界是 4 小时，窗口外那 2 小时仍会白试（每分钟一次）；若真实边界是 8 小时，最后 2 小时会提前让给别的桥。两种偏差都只影响「哪座桥发」，不影响消息内容与安全。
- 声明窗口后，卡住的交付**不再有回执错误**——错误从「`ret=-2`」变成「根本没发」。所以核心侧必须把 `waitReason` 露出来（`pending` + `wait_reason=window` 在面板与告警里显示成「等推送窗口」，而不是普通「待发送」），否则这次修复会换一种方式继续沉默。该改动在 `dsh-my-superagent`（ADR-0090 的提示面）。
- 桥从此不主动纠正「窗口已关」的判断：如果服务端实际放宽了有效期，桥要等核心按旧窗口跳过它，表现为「早一点不发」，不会自动变长。
