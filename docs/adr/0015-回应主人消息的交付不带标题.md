# 0015. 回应主人消息的交付不带标题

- 状态：已采纳（修订 [ADR-0008](0008-微信原生Markdown与出站文本过滤.md) 的组装规则）
- 日期：2026-11-10

## 背景

桥把一条交付拼成微信文本时，标题与正文都用空行隔开依次发。这对主动推送（`长任务完成「周报」`、`在等你回话「X」`）是对的：主人要知道这条是什么。

但一问一答不需要：核心把主人自己那一轮的回复标题写成「回复」（`replyReport`），桥照发，微信里每条回答顶上就多一行「回复」。核心的 [ADR-0030](../../../dsh-my-superagent/docs/adr/0030-回复状态行.md) 已经写明「回到原消息的回复按引用就能对上，不另加标题」，协议里对应的字段是 `Delivery.inReplyTo`——`dsh-im-infoflow` 的 `deliveryMarkdown` 也是这么做的：有 `inReplyTo` 只发正文，没有才带标题。微信桥漏了这条规则。

## 决策

- `composeDeliveryText` 在 `delivery.inReplyTo !== undefined` 时**丢掉标题**，只发正文与交互文字；标题为空时行为不变。
- 主动推送（没有 `inReplyTo`：长任务提醒、提问提醒、失败提醒、摘要）照旧带标题。
- 标题仍按 [ADR-0008](0008-微信原生Markdown与出站文本过滤.md) 过滤 Markdown；这条规则只决定发不发，不改内容。

## 后果

- 微信里的一问一答变成「问一条、答一条」，不再每条回答顶一行「回复」。
- 桥的行为与核心的标题约定、与 `dsh-im-infoflow` 对齐；核心以后给回复换标题，微信侧也不会跟着变。
- 代价：如果哪天核心想用标题传达回复里的额外信息（例如「这一轮被拦下」），那种交付必须不带 `inReplyTo` 才看得见——目前这类结局本来就走主动推送，不受影响。
