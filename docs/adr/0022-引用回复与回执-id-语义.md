# 0022. 引用回复与回执 id 的语义

- 状态：已采纳
- 日期：2026-11-13

## 背景

用户在微信里引用一条机器人发出的提醒、回一句话，希望这句话直接回到提醒所属的会话，而不是重新进前台。要做到这一点，核心必须把「被引用的那条消息」认回「是哪一次交付、哪个会话」。

核心已有的接线是：出站回执 `Receipt.bridgeMessageId` 落进投递记录；入站草稿 `OwnerMessageDraft.replyTo` 带被引用消息的 id；核心用两者做全等比较。也就是说，桥必须让这两个 id 是**同一个平台 id**。

## 决策

1. **回执写平台 `message_id`，不写桥自造的 `client_id`**。发送响应里平台会回 `message_id`（`docs/protocol/` 有字段事实），用户引用时 `ref_msg` 带回来的就是它。桥自己的 `dsh-im-wechat:<uuid>` 用户永远看不到，无法回指。
2. **分条交付记录全部平台 id**（`bridgeMessageIds`），`bridgeMessageId` 仍带最后一条兼容旧核心。引用中间那条也要能认回，否则引用被拆开的回答会退回前台。
3. **图片-only 交付记最后一张图的 id**。图片也是交付的一部分，用户引用那张图同样应该能认回；不能因为「没有文字」就没有回执 id。
4. **桥静态声明 `quoteReply`，核心按「任一桥支持」决定提醒文案**。声明是 best-effort：平台不回 `message_id` 时，桥只是少一个 id 并告警一次，不会撤回声明。

## 后果

- 主路径成立：引用提醒、引用图片，都能把话转回那个会话。
- 旧核心只读 `bridgeMessageId`（最后一条）时，引用中间某条分条仍会静默退回前台；新核心读 `bridgeMessageIds`，每条都认。
- 静态声明的代价：平台改名、灰度或某条路径不回 `message_id` 时，核心仍会在提醒里写「引用回一句」。桥在发送成功却没有 id 时按小时告警一次，让协议漂移在面板可见。

## 否决的方案

- **保留本地 uuid，另加一个平台 id 字段**：要改核心 `ReceiptSchema` 与投递索引，是跨仓契约变更；核心只认一个字段，多一个只会让两边各记一份、更难对齐。
- **回执存全部 id**：索引与查询都要改，且目前只有「引用最后一条」这个真实场景。
- **动态撤回 `quoteReply`**：核心按「任一桥支持」判定，撤回会连带影响同账号的其它桥；而且撤回时机无法可靠判断。
