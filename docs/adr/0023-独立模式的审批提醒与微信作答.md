# 0023. 独立模式的审批提醒与微信作答

- 状态：已采纳（补齐 [ADR-0006](0006-问题提醒与长任务提醒归谁发.md) 在独立模式只覆盖「提问」的缺口）
- 日期：2026-11-15

## 背景

独立模式（未接入核心）一直只接管 `user-questions/request`：提问推到微信、主人在微信作答。工具授权走的是另一条 waterfall `approval/request`，本插件从未注册，所以需要授权的工具调用只会在 Web 端等人；主人在微信里长时间看不到提示，回合就这么卡着。

同时暴露两个可用性问题：

1. **没有开关**：提问与提醒只能跟着「接入微信」总开关一起开合，关掉就连收消息一起没了。
2. **一有提问就推**：用户通常正开着 Web 端，很多问题几十秒内就在 Web 端答掉了，微信那条提醒纯属打扰。

## 决策

**把审批也接进独立模式，并给两条提醒加同一个「等多久再提醒」窗口。**

1. **新增开关 `questionReminders`（默认开）与等待时间 `questionDelayMinutes`（默认 5 分钟，0–120，0 = 立即）**，落在 `config.json`，面板在「消息与提醒」区提供开关与分钟输入，`HOST_CONTRACT` 递增到 4。开关的值写坏时按**关**处理：它决定「微信消息能否批一次工具授权」，不静默恢复。
2. **先让 Web 端拿请求，再等窗口**：进入监听器后立刻 `next()`，然后和等待计时器竞速。窗口内 Web 答完就一条微信都不发；窗口到点才发提醒。两条 waterfall 的「没人接」表达不同——提问是抛 `NO_PROVIDER`，审批是解析成 `unavailable`——两者都按「Web 不在」继续等主人，不当作答案返回。
3. **审批可以回微信处理**：提醒文案写明「回复「批准」或「拒绝」」。只认明确的整词（批准/同意/approve/yes；拒绝/不批准/不同意/deny/reject/no），**不收单字母 `y`/`n`**（一次误发就是一次真实授权）。命中批准回 `allowed-once`、命中拒绝回 `rejected`，两者之外一律不认领，交给普通消息路径，**绝不猜**。这是宿主的失败关闭语义：`approval/request` 的缺省结局是 `unavailable`。
4. **只接管自己能负责的部分**：仍是只提醒根会话、只认扫码登录的主人、独立模式才生效（`ownFeaturesActive`）；接入核心后整段沉默（ADR-0006）。窗口内没人处理就把请求交回 Web（**交回**是 `return next()` 那条链的结果，不是抛错——抛错会被宿主归一成拒绝，Web 端随后的点击就作废了）。
5. **归属按「最后发的那条提醒」**：提问的单题自由输入会认领任意文本，不排序的话审批的「批准」会被它吞掉。顺序由 `ReminderCenter` 记一处（**不是**两个 broker 各记一个序号——两个独立计数器不可比）。
6. **多条授权可指定**：提醒带编号（`需要你授权 #3：bash`），回复可带编号（`批准 3`）；不带编号时认**最后一条**，结算后回一条「已批准：bash（#3）」，让主人能发现批错对象。
7. **提醒文本只带必要的宿主字段**：工具名与原因（压成一行、截断 200 字符），其余用固定提示。原因来自宿主，可能含路径/命令片段，也可能是模型被诱导写进去的敏感串——不原样整段出网。
8. **提醒单独节流**：交付走 `superagent/quota.ts` 的账本，提醒不走。给提醒一个小预算（6 条/分钟、间隔 2 秒），超了就不发、把请求交回 Web——排队到点才发出的提醒已经过时，更容易让主人批错。
9. **跨重启去重**：入站是 at-least-once（批次中途停机会刻意不推进游标），核心在接入时按 `messageId` 兜底，提醒回复没有核心。最近 50 条已消费的消息身份落到状态目录，重启后同一条「批准」不再批一次新授权。

## 否决的方案

- **默认 0 等待（有提问就推）**：否。多数问题在 Web 端几十秒内就答完，每条都推一遍是纯打扰；需要立刻提醒的把等待时间调到 0 即可。
- **任意自由文本都能代答审批**：否。那是把「猜」变成授权；审批只认整词，模糊的话交回普通消息路径。
- **核心模式也接管审批**：否。ADR-0006 的互斥不变——接入核心后同一条提醒会来两遍，授权也该由核心自己决策。
- **按 `agents.roots()` 判根会话**：否。宿主 0.2.1 起已删除该方法，按它判定会得到恒空集合，把全部提醒静默关掉；改读 `agent.session.header.origin`。

## 后果

- 主人不在 Web 端时，工具授权也能从微信批掉，回合不再干等；在 Web 端时默认 5 分钟内不打扰。
- **安全边界扩大了一格**：微信消息现在能决定一次工具授权。约束是「只主人 + 只根会话 + 只认明确关键词 + 不代答 + 缺省失败关闭 + 跨重启去重」；接入核心后这条路径不生效（核心自己决定授权）。ADR-0006 的「自有功能与核心互斥」不变。
- 等待窗口让审批最多晚 5 分钟才提醒，长回合会更慢；把 `questionDelayMinutes` 调成 0 即恢复「立刻提醒」。
- 提醒节流意味着极端情况下（一分钟内超过 6 条）会有提醒发不出去，那些请求留在 Web 端处理。
- 新增四个模块：`approvals.ts`（审批 broker）、`reminder-center.ts`（两个 broker + 设置）、`reply-pending.ts`（两者共用的待答机械件）、`send-gate.ts`（提醒节流）；面板设置动作移到 `panel-actions.ts`，`runtime.ts` 相应瘦身（500 → 486 行）。
