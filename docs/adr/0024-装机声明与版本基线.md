# 0024. 装机声明：DSH 与 Node 的版本基线

- 状态：已采纳（修订 [ADR-0020](0020-发布走CI与npm可信发布.md) 后果里「`engines` 仍写 22.19+」那句）
- 日期：2026-11-15

## 背景

1. **包对宿主没有任何机器可读的要求**。`package.json` 只写了 `engines.node: >=22.19`，既没有 DSH 版本门槛，也没有任何字段告诉 npm 与装机方「这个包装在哪」。老 DSH 上装进来的是一个用不上、甚至加载不起来的面板；本仓库的 `HOST_CONTRACT`、`dsh.client.inject`、监听宿主事件的方式却全是按 0.2 起的契约长出来的，只写在文档里。
2. **DSH 的门禁只看两处**。`dsh-app-boot` 的 `evaluatePluginCompatibility`：有 `engines.dsh` 就只看它（"An own `engines.dsh` range decides alone"）；没有时退化看 `peerDependencies` 里所有 `@deepseek-ai/dsh` 与 `@deepseek-ai/dsh-*` 的范围。两者并存时 peer 完全不参与判定。范围按 `includePrerelease` 判，所以基线本身可以写成预发布。
3. **本仓库有一条零依赖门禁**。`scripts/verify-package.mjs` 要求 `dependencies`、`peerDependencies`、`optionalDependencies` 全空，这是 [ADR-0001](0001-基于openclaw-weixin的零依赖微信桥.md) 的落地：防「顺手引个库」，也防宿主包的第二份副本（Symbol 查表会失效）。要声明兼容范围，就必然碰这条。

## 决策

**在 `package.json` 里声明三个互相不矛盾的版本事实，并给零依赖门禁开一个只放行「声明」的口子。**

1. **`engines.node` 只留 24**（`>=24.0.0`）。门禁 CI 固定 24.x；node 22 的 `node --test` 会把依赖 `AbortSignal.timeout`（定时器 unref）的直连用例判成 `cancelledByParent`，本地全量会看到 9 条假失败。写 `22.19+` 等于承诺一件从没验证过的事。
2. **`engines.dsh: ">=0.2.2-rc.1 <0.3.0"`**：下界是钉住的基线，上界卡在 0.3。宿主事件名、`approval/request` 的 fallback 语义（解析成 `unavailable` 而不是抛错）、`agents.get/list` 的形状都是按 0.2 起的宿主验证过的，0.3 不能默认兼容。
3. **`peerDependencies` 只写两个平台包**：`@deepseek-ai/dsh`（同一基线范围）与 `@deepseek-ai/cordis`（`^4.0.1`，插件本身是 Cordis 插件）。**两个都标 `peerDependenciesMeta.optional`**：它们由宿主提供，npm 一装就是第二份副本；optional 让它们只作声明，不触发安装。
4. **门禁把「声明」与「安装」分开**：`dependencies`、`optionalDependencies` 仍必须为空；`peerDependencies` 只允许 `@deepseek-ai/` 开头的平台包，且每一项必须标 optional。第三方包、宿主包的非可选 peer 依旧直接失败。
5. **客户端包不写进 peer**。`dsh.client.inject` 里的四个包与运行时同版本、由 Web 模块表在页面里提供，宿主安装目录里未必是独立包（`dsh-client-ui-slots`、`dsh-client-ui-primitives` 在 `node_modules` 里就查不到）。顺序需求已经由 `dsh.client.inject` 表达（结论与 `dsh-git-panel` ADR-0032 一致），版本兼容由 `engines.dsh` 一并覆盖。

## 否决的方案

- **只写 `peerDependencies`，不写 `engines.dsh`**：否。DSH 会退化成「按 peer 反推门槛」，以后每加一个 `@deepseek-ai/dsh-*` peer 就顺手改了装机门槛，而且门槛散落在多处；`engines.dsh` 是唯一能一处决定的地方。
- **保留 `node: >=22.19`**：否。CI 只跑 24，`engines` 写着 22 却从没在 22 上跑过全量；那 9 条假失败会把新人的注意力引到与产品无关的红灯上。
- **把四个客户端包也写进 peer**：否。它们不进宿主 `node_modules`，写进去只会让 npm 报一份不存在的 peer；即便装上，页面用的仍是 Web 模块表里那份。
- **为这次改动静默删掉零依赖门禁**：否。门禁红一次就整条删掉，这个仓库最该守的两个不变量（不引第三方库、不装宿主副本）就一起没了；放行条件必须写死成「`@deepseek-ai/*` 且 optional」。

## 后果

- DSH < 0.2.2-rc.1，或 0.3 以后的版本，装不上也激活不了：安装时会给出明确诊断，并提供精确到版本对的豁免入口（`dsh plugin allow-version`）。已经装好的老组合不受影响。
- 装机方在 `npm view` 与插件详情里能看到兼容范围；本仓库 `npm install` 不会因为 peer 去拉 DSH 或 Cordis。
- 门禁多一条要维护的规则：新增 peer 必须同时给 `peerDependenciesMeta.optional`，`test/unit/manifest.test.ts` 与 `scripts/verify-package.mjs` 都会拦。
- 代价：**已经发布出去的 0.1.0 没有这些字段**，门槛只在下一次发版后对「新装的 0.1.0 之后的版本」生效；想让老版本也受管，得发一个新版本并在 `docs/releases/` 写清门槛变化。
