# 0026. 独立模式会话的推理等级

- 状态：已采纳（修订 [ADR-0025](0025-独立模式会话的模型.md) 的选择形状：`{provider, model}` 扩成 `{provider, model, reasoningEffort?}`；0025 的钉模型机制、清空语义与目录来源不变）
- 日期：2026-11-15

## 背景

ADR-0025 把独立模式的会话固定到某个模型，但选择只到 `provider/model` 两层。宿主的模型目录其实每个模型都带 `reasoning.efforts` 与可选的 `defaultEffort`（`sessionController.modelCatalog()` 的返回里就有），会话的 `model/selection` 事件也带 `reasoningEffort`。主人想固定「便宜模型 + 高推理等级」或「强模型 + 低推理等级」时，只选模型做不到：推理等级会跟着模型自己的默认走。

同仓的 `dsh-git-panel` 已有同形的三级选择（provider → model → effort），交互与数据形状都验证过；本插件沿用同一套选法，避免同一个面板里两套选模型的习惯。

## 决策

1. **配置与契约形状**：`directModel: { provider, model, reasoningEffort? }`，`status.direct.model` 与 `direct.set` 的 `model` 同形。`reasoningEffort` 缺省、空白或 `null` 表示用模型自己的默认推理等级；落到配置里时不写空字段。名字直接用宿主 `ModelSelection.reasoningEffort`，两半不用再翻译。
2. **目录**：仍然只读 `sessionController.modelCatalog()`，不新增宿主服务。拍平后每个模型带上 `efforts: {id, label}[]` 与可选的 `defaultEffort`；没有推理等级的模型给空数组，面板据此禁用第三级。
3. **生效方式沿用 0025**：`agents.get(sessionId).model.select({ provider, model, reasoningEffort? })`，每次提交前幂等钉一次，面板保存后立刻对已绑定的会话试一次。去重键包含推理等级——**只改推理等级也是一次新选择**，需要再钉一条 `model/selection`。
4. **保存校验**：模型必须仍在目录里（0025 的规则），并且推理等级必须是该模型声明的档位之一；不在档位里按 `invalid-config` 拒绝，要求重选。目录整体读不到、或该 provider 自己读失败时放行（「未校验」，与 0025 对模型的处理一致）。**清空推理等级**（保留模型）会把会话切回模型默认，已绑定会话立刻生效。
5. **面板三级选择**：
   - 第一级 provider 的第一项是「跟随 DSH 默认」并带出宿主默认路由（含推理等级名）；选了它就等于清空整条选择；
   - 第二级只列当前 provider 的模型，换 provider 时同名模型保留、否则清空；
   - 第三级的第一项是「模型默认」，换模型时新模型不支持的旧推理等级清掉；
   - 已保存的值不在目录里（模型或推理等级）时补一行原文并标「已下架 / 未校验」，**不清空、不静默回退**；旧推理等级即使模型已不提供，第三级仍可点开清回默认；
   - 三级都选完再按一次「保存」，不在每次级联时写盘——半条选择（只有 provider）不该进配置文件。
6. **契约**：`HOST_CONTRACT` 与客户端 `REQUIRED_CONTRACT` 从 5 加到 6（`models.list` 的每行多了 `efforts` / `defaultEffort`，`direct.set` 的 `model` 多了可选字段）。

## 否决方案

- **不在面板校验推理等级，交给适配器报错**：`model.select` 会把任何字符串写进会话，适配器拿到表外的 id 没有兜底，错误要等到下一次模型请求才出现，微信侧只看到这一轮失败，很难对到「刚才选错了推理等级」。面板按目录先拦，错误信息能直接指回选择。
- **选中模型时自动写死它的 `defaultEffort`**：目录里的默认只是适配器当前的建议，写死等于把会话钉在那一刻的档位上；留空表示「用模型默认」，以后适配器调整默认推理等级时自动跟随。
- **推理等级另立一个配置项**（如 `directEffort`）：两半要自己保证 provider/model/effort 的组合一致，清空与级联各写一份很容易漂移；放在同一条选择里，会话事件本身就是完整的 `model/selection`。
- **像 git-panel 那样直接用 `ctx.llm` 读目录**：多一个宿主服务依赖，也多一套与 `sessionController.modelCatalog()` 并行的目录实现；后者已经带推理等级，只留一个来源。

## 后果

- 微信侧可以固定「模型 + 推理等级」，Web 端的默认模型与推理等级都不受影响。
- 推理等级被适配器下架后：面板把已保存的推理等级标成「已下架」并要求重选，保存会被宿主拒绝；推理等级留空则用模型自己的默认。
- 清空整条模型（`null`）仍只影响以后新建的会话（0025 的语义），因为会话里记下的选择撤不回来；但**只清空推理等级**会立刻把已绑定会话切回模型默认——两者不同，面板只在清空整条选择后提示「先重置绑定」。
- 契约 5 → 6：新面板 + 旧 host 会提示重启并锁住独立模式设置；旧面板 + 新 host 不会被判成旧宿主，面板照常能改模型，但它不认识 `reasoningEffort`，保存时只发 `{provider, model}`，会把已保存的推理等级清掉。要把「没传」与「显式清空」分开表达才能兼容旧面板，而本面板清空本来就是省略字段，两者冲突，接受这个代价。
- 把三级逻辑加进 `src/client/logic.ts` 后它会超过 500 行，因此模型相关的纯逻辑拆到 `src/client/model-route.ts`；`src/host/runtime.ts` 这次没有增长（仍贴着 500 行上限，下个功能得先拆装配层）。
