# 0031. 失败提醒独立开关

- 状态：已采纳（修订 [ADR-0011](0011-失败立刻提醒.md) 的「失败关不掉」；判据移入 AGENTS.md 与 `src/host/long-tasks.ts`）
- 日期：2026-11-21

## 背景

[ADR-0011](0011-失败立刻提醒.md) 定了「失败立刻提醒、不受长任务开关影响」，代价里写明「关闭开关不再等于完全静默：失败仍会来。有意的」。当时没有第二个开关可用，一条 `configure(false)` 既要关完成提醒，失败只能被放行，否则主人对短任务的报错完全无感。

面板与配置长出第二条旋钮之后，「关掉提醒」有了两种意图：**只是嫌完成提醒吵**，和**这个阶段不想被任何东西打扰**。前者继续由自有功能总开关管，后者没有出口——夜间/离线场景下失败提醒照样推，主人只能卸载插件。

## 决策

**失败提醒独立成开关 `failureReminders`（面板「失败任务提醒」），默认开；关掉后失败静默，且不降级成完成提醒。**

1. 归属：开关只在**提醒器层**（`long-tasks.ts`）生效，与完成提醒的 `configure` 分开存两个字段；完成提醒仍看「自有功能生效 + 超阈值」，失败只看 `failureReminders`。
2. 关掉后失败不降级：失败不看阈值、不看是否插过话，是既定语义；关掉就是**不发**，不是「改成按阈值的完成提醒」，否则同一次失败会在阈值到点时以「已完成」的面目再出现一次。
3. 主人自己停的（`reason.reason.kind === 'user'`）在两种开关下都不提醒，这条不变。
4. 默认开：与 ADR-0011 的「失败是必须知道的事」一致，缺省行为与过去相同；写坏的配置值也回落到开（通知不是授权，静默关掉比多一条提醒更难发现）。
5. 落盘与展示：配置键 `failureReminders` 进 profile 静态配置与面板 `config.json`（面板值优先），状态里回 `failureReminders`，面板 RPC 契约升到 10（`longtask.set` 接受 `{minutes?, failureReminders?}`）。
6. 提醒文案：「长任务提醒」统一改为「长程任务提醒」（标题、面板、README），与 dsh-im-infoflow 的叫法一致；失败标题仍是「任务失败」。

## 否决的方案

- **继续「失败关不掉」**：吵的场景没有出口，是本次要解决的问题本身。
- **复用完成提醒的 `configure` 一个开关**：会把失败一起关掉，回到 ADR-0011 之前的「失败没下文」。
- **关掉失败后降级成阈值提醒**：同一次失败会以「已完成」的面目延迟出现，误导比不发更糟。
- **失败时仍然发、只在面板折叠**：微信侧照样响，没有解决打扰。

## 后果

- 两个开关都开（默认）= 与 ADR-0011 行为一致；只关完成 = 只报失败；只关失败 = 只报超阈值完成；都关 = 完全安静。
- 失败提醒从此**可被静默**，ADR-0011 里「关不掉是刻意的」不再成立，本篇取代它；判据与不变量写在 `AGENTS.md` 与 `test/unit/long-tasks.test.ts`。
- 代价：多一个配置键与一处面板开关；「离线时段静默失败」换来的是那段时间内的失败不会被微信提醒——主人要靠面板的「最近错误」回看。
- 旧配置文件没有这个字段，读回缺省为开，升级后行为不变。
